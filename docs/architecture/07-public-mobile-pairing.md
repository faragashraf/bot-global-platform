# Public Mobile Pairing V1

Bot Global Public Service owns the public mobile-pairing boundary for systems
such as internal Connect V2.

Topology:

```text
Internal platform
→ Generic Platform Client machine authentication
→ Bot Global Public Service
↔ Mobile app over the Internet
```

The mobile app does not call the internal platform directly.

## Security boundary

The QR payload is an opaque, single-use pairing token generated by Bot Global.
It must not contain usernames, email addresses, employee numbers, roles,
permissions, access tokens, refresh tokens, passwords, OTPs, or personal profile
data.

Only the SHA-256 hash of the pairing token is persisted. The raw token exists
transiently in the create response so the authenticated machine client can render
the QR.

## Persistence

Pairing uses the module-owned database boundary:

- connection string: `ConnectionStrings:Pairing`
- schema: `pairing`
- migration history: `pairing.__EFMigrationsHistory`
- table: `pairing.PairingChallenges`

The record stores:

- `PairingChallengeId`
- server-derived `PlatformClientId`
- `TokenHash`
- `CreatedAtUtc`
- `ExpiresAtUtc`
- `Status`
- optional `CorrelationReference`
- completion timestamp and bounded mobile installation metadata after claim

There is no cross-module foreign key to PlatformClients; ownership is a value
reference derived from the authenticated machine principal.

## Machine create

```http
POST /api/pairing/challenges
Authorization: PlatformClient
Capability: pairing:create
```

Request:

```json
{
  "correlationReference": "opaque-client-reference"
}
```

`correlationReference` is optional, server-side only, and must be treated as an
opaque machine-client reference. It is not placed in the QR and is not provided
by the mobile app.

Response:

```json
{
  "challengeId": "00000000-0000-0000-0000-000000000000",
  "qrPayload": "opaque-pairing-token",
  "expiresAtUtc": "2026-08-14T12:03:00+00:00"
}
```

The default lifetime is 3 minutes.

## Machine status

```http
GET /api/pairing/challenges/{challengeId}
Authorization: PlatformClient
Capability: pairing:status
```

The authenticated machine client can read only challenges it owns.

Response states:

- `pending`
- `completed`
- `expired`

Pending challenges are reported as `expired` after `expiresAtUtc`; correctness
does not depend on background cleanup.

Recommended polling interval for V1 is 2–5 seconds. SignalR is not required for
Pairing V1.

## Mobile claim

```http
POST /api/mobile/pairing/claim
```

Request:

```json
{
  "pairingToken": "opaque-pairing-token",
  "device": {
    "platform": "android",
    "installationId": "app-generated-random-installation-id",
    "deviceName": "optional bounded display name",
    "appVersion": "1.0.0"
  }
}
```

`installationId` is generated by the app installation. It is not an IMEI, serial
number, MAC address, advertising ID, or permanent Android hardware identity.

Mobile claim does not require machine credentials. It does not issue Connect
sessions or durable device records in V1.

## Replay and concurrency

A challenge can transition from `Pending` to `Completed` once. EF persistence
uses a concurrency token on the challenge row. Concurrent claim attempts against
the same token result in exactly one successful completion; later attempts fail
as invalid, expired, or already used.

## Logging

Do not log:

- raw pairing tokens
- token hashes except controlled/truncated diagnostics if later approved
- platform client secrets
- mobile credentials

Safe operational identifiers are challenge id, platform client id, result state,
timestamps, and request correlation ids.
